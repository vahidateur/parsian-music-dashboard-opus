# پارسیان — داشبورد مدیریت آموزشگاه موسیقی

پنل مدیریت یکپارچهٔ «آکادمی موسیقی پارسیان» — تجربه‌ای فارسی، راست‌به‌چپ و سینمایی برای ادارهٔ روزانهٔ یک آموزشگاه موسیقی حرفه‌ای.

> «یک مرکز فرماندهی مدرن برای ادارهٔ یک آکادمی موسیقی»

## وضعیت مهندسی

نقطهٔ شروع برای هر نشست یا مشارکت‌کنندهٔ تازه:
[`docs/engineering/PROJECT_STATE.md`](docs/engineering/PROJECT_STATE.md) — فاز جاری،
checkpoint‌های ماندگار، وضعیت اعتبارسنجی (تست / typecheck / build)، محدودیت‌های شناخته‌شده و
اقدام بعدی. سه سند همراه آن:
[`docs/engineering/PHASES.md`](docs/engineering/PHASES.md) (تاریخچهٔ فازها)،
[`docs/engineering/DECISIONS.md`](docs/engineering/DECISIONS.md) (تصمیم‌های معماری و دلیلشان) و
[`docs/engineering/OPEN_ITEMS.md`](docs/engineering/OPEN_ITEMS.md) (کارهای باز، دسته‌بندی‌شده).
این چهار سند با `src/__tests__/projectState.test.ts` اعتبارسنجی می‌شوند، پس هر ادعای نادرست در
آن‌ها تست را قرمز می‌کند.

### اجرای یکپارچه (Laravel + React)

```bash
npm run dev:full
```

- فرانت‌اند: http://localhost:5173 — ترکیب `client` با `APP_TARGET=client` و `VITE_DATA_SOURCE=api` (بدون بازگشت پنهان به دادهٔ نمایشی).
- API: http://127.0.0.1:8080/api/v1 (بررسی سلامت: `/up`) — درخواست‌های `/api` از طریق پراکسی Vite به Laravel می‌رسد.
- این دستور **migrate یا seed اجرا نمی‌کند** و کاربر نمی‌سازد؛ پایگاه داده و کاربر ورود باید از قبل وجود داشته باشند.
- پیش‌نیاز: PHP روی PATH، `composer install` در `backend/`، و فایل `backend/.env` با `APP_KEY`.
- `npm run dev` بدون تغییر است: ترکیب نمایشی/محلی و بدون نیاز به بک‌اند.

> **اجرای همزمان بک‌اند و فرانت‌اند ≠ اتصال آن‌ها.** `npm run dev` ترکیب نمایشی است: داده را
> در `localStorage` همان مرورگر می‌خواند و می‌نویسد و **هیچ درخواستی به بک‌اند نمی‌فرستد**؛
> تغییرات شما در پایگاه داده دیده نمی‌شود. برای کار با دادهٔ واقعی حتماً `npm run dev:full` را
> اجرا کنید. سرور توسعه در هر دو حالت، منبع دادهٔ خودش را در ترمینال اعلام می‌کند و اگر بک‌اندی
> روی `127.0.0.1:8080` بالا باشد ولی از آن استفاده نکند، هشدار می‌دهد.

### منابع محلی ابزارهای عامل

بخشی از ابزارهای کار با عامل‌های هوش مصنوعی در این مخزن **منتشر نمی‌شود**. مسیرهای زیر فقط روی
رایانهٔ توسعه‌دهنده وجود دارند، در `.gitignore` فهرست شده‌اند و عمداً از snapshot منتشرشده بیرون
مانده‌اند:

- `.agents/` — مهارت‌های محلی عامل
- `.opencode/agents/` · `.opencode/skills/` — عامل‌ها و مهارت‌های OpenCode
- `.kiro/skills/` · `.kiro/hooks/` · `.kiro/settings/` — مهارت‌ها، قلاب‌ها و تنظیمات محلی Kiro
- `opencode.json` · `skills-lock.json` — پیکربندی و قفل مهارت‌ها

نبودشان در یک clone تازه **عمدی** است؛ هر توسعه‌دهنده ابزارها و مهارت‌های محلی خود را خودش تنظیم
می‌کند.

### راه‌اندازی محلی مجوزهای OpenCode (پس از clone)

مخزن منتشرشده هیچ `opencode.json` ندارد. برای فعال‌کردن لایهٔ ابزاری روی رایانهٔ خود:

1. یک `opencode.json` محلی در ریشهٔ مخزن بسازید. این فایل در `.gitignore` است و هرگز commit نمی‌شود.
2. قواعد موردنظرتان را در آن بنویسید؛ برای نمونه `deny` برای `git push*`، `ask` برای
   `git commit*` / `git add*` / `git merge*`، و هر قاعدهٔ `read`/`edit` که برای محیط خود می‌خواهید.
3. `skills-lock.json` هم محلی است و فقط هنگام نصب مهارت‌های محلی ساخته می‌شود؛ آن را هم commit نکنید.
4. پیش از تکیه بر هر ادعای «مسدودشده در سطح ابزار»، مطمئن شوید پیکربندی واقعاً بارگذاری شده
   است (برای نمونه با `opencode debug config`).

سه لایه را از هم جدا نگه دارید:

- **راهنمای مخزن** (`AGENTS.md`، `.opencode/specs/`، `.kiro/steering/`) فقط **INSTRUCTION-ONLY**
  است: قاعده را بیان می‌کند، ولی هیچ مکانیزمی آن را مسدود نمی‌کند.
- **پیکربندی محلی شما** (`opencode.json`) تنها تا وقتی موجود و بارگذاری‌شده باشد
  **TOOL-ENFORCED** است.
- **تصمیم انسانی (HUMAN APPROVAL)** — اجازهٔ صاحب پروژه در همان گفتگو برای انتشار، merge یا حذف،
  مستقل از هر پیکربندی، همیشه لازم است.

پیکربندی شخصی — پلاگین‌ها، اعتبارنامه‌ها و مسیرهای ماشین — را در هیچ فایل tracked قرار ندهید.

در مقابل، این‌ها بخشی از مخزن منتشرشده‌اند: مشخصات مشترک ابزارهای عامل در `.opencode/specs/`،
راهنمای مشترک پروژه در `.kiro/steering/`، و گردش‌کارهای GitHub Actions در `.github/workflows/` —
از جمله گردش‌کار CI فرانت‌اند که بخشی از فرایند اعتبارسنجی است.

کد برنامه (`src/`)، مستندات پروژه (`docs/`) و پیکربندی مشترک همچنان در مخزن می‌مانند.

## زبان طراحی

- **تیرهٔ کنسرواتوار** (پیش‌فرض) و **شیشه‌ای** (گزینهٔ ثانویه) — از تنظیمات → ظاهر.
- **لهجهٔ کنترل‌شده**: طلایی صحنه، کهربای ساز، بنفش رزونانس — فقط سه گزینه، نه رنگ‌های پراکنده.
- همهٔ اجزا از توکن‌های معنایی (`gold-*` → متغیر لهجه، `ok/warn/danger/info/violet` ثابت) تغذیه می‌شوند؛ رنگ سخت‌کد در صفحات نیست.
- تراکم (راحت/فشرده) و حرکت (روشن/خاموش) از همین سیستم اعمال و در `localStorage` ذخیره می‌شوند.
- حرکت: ریتم بر پایهٔ ♩ ۱۲۰bpm؛ `prefers-reduced-motion` و تنظیم «حرکت» هر دو رعایت می‌شوند.

## بخش‌های محصول

داشبورد (مرکز فرماندهی) · هنرجویان · مدرسین · کلاس‌ها · برنامه‌ریزی · حضور و غیاب · مالی · گزارش‌ها · پیام‌ها · کتابخانه · تنظیمات · سیستم طراحی.

- **هوش آموزشگاه** یک الگوی محصول/UX است (سیگنال → شواهد → بینش → اقدام) با دادهٔ نمایشی — ادعای هوش مصنوعی واقعی ندارد.
- **دادهٔ نمایشی** در مالی و گزارش‌ها صریحاً برچسب خورده است و ساختار داده‌ها برای جایگزینی با بک‌اند واقعی آماده است.
